# Фитнес-сводка — контекст проекта

Этот файл — сжатая память всего, что было решено и построено в проекте.
Он написан для того, чтобы новая сессия (в том числе в Claude Code) не начинала
с нуля и не переоткрывала уже принятые решения заново.

Приложение делает одно: берёт данные тренировок и восстановления, которые
**Garmin Connect пишет в Health Connect**, и складывает их в честную сводку за
день и за неделю. Оно ничего не измеряет само и ничего не пишет обратно.

Проект — младший брат `atomic-habits-tracker`: те же стек, архитектура,
принципы обновления и стиль. Осознанное повторение, а не совпадение.

## Почему Health Connect, а не Garmin Connect API

Это главное архитектурное решение, и его **не нужно пересматривать без новых
фактов** — оно было принято после проверки, а не по умолчанию.

Официальный Garmin Connect API (и Health, и Activity) — **push-only**. Прямых
REST-эндпоинтов «отдай активности за период» нет, они прямо запрещены условиями
API. Garmin шлёт PING/PUSH на **публичный HTTPS-webhook**, и только после этого
можно забрать данные по callback-URL.

Из этого следует то, что и определило архитектуру:

- **Android-приложение не может быть webhook-приёмником.** Вариант «APK + Garmin
  API» без серверного куска не собирается физически.
- Self-serve режим существует, но даёт доступ только к собственным данным, а
  регистрация периодически закрыта; заявки от физлиц отклоняют — нужно юрлицо.

Рассматривались три пути:

| | Как | Сервер | Что даёт |
|---|---|---|---|
| A | Self-serve API + Cloud Function-вебхук | нужен | всё, что отдаёт API |
| B | **Health Connect** ← выбран | не нужен | шаги, калории, дистанция, пульс, сон, тренировки |
| C | Неофициальная авторизация (garth-подобная) | не нужен | всё, включая Body Battery |

Выбран **B**: бесплатно, без регистрации, без сервера, без серых зон ToS,
работает офлайн.

**Цена решения, которую надо помнить:** Body Battery, Stress, Intensity Minutes,
Training Load, Training Status, VO2max, HRV Status в Health Connect отсутствуют
как типы данных. Их здесь не будет никогда — не потому что не реализовано, а
потому что Garmin их туда не передаёт. Если они однажды понадобятся —
это переход на вариант A или C, то есть другая архитектура, а не новый экран.

Цепочка данных целиком:

```
Часы Garmin ──BLE──> Garmin Connect ──> Health Connect ──> Room ──> UI
                                                            └──> Firestore (между устройствами)
```

Требует Android 14+: именно с него Garmin Connect умеет писать в Health Connect.
На 26..33 приложение ставится и запускается, но честно сообщает, что Health
Connect недоступен.

## Стек и структура

Kotlin + Jetpack Compose (Material3), Room (единственный источник правды для
UI, offline-first), Firebase Firestore (синхронизация поверх Room, не вместо
неё), Firebase Auth (Google Sign-In). Без ViewModel — Compose-локальное
состояние (`collectAsState`/`remember`/`LaunchedEffect`) напрямую поверх Flow
из репозиториев. Осознанное упрощение под масштаб одного разработчика.

```
data/          Entity + Dao + Repository + агрегация недели
health/        HealthConnectManager (доступ/разрешения), Reader (чтение), SyncManager (в Room)
sync/          FirestoreSyncManager, AuthManager, FirebaseSetup
debug/         AppLog — внутриприложенный лог, см. «Диагностика» ниже
ui/<screen>/   один пакет на экран
ui/components/ переиспользуемые composable, включая графики
export/        DataExporter — JSON-экспорт для анализа
update/        UpdateChecker + ApkInstaller (обновление по GitHub Releases)
util/          чистые функции без побочных эффектов
navigation/    Routes + NavHost + нижнее меню
```

Текущая версия БД — **v1**. Каждая будущая миграция аддитивна, ничего не
удаляется деструктивно, никогда `fallbackToDestructiveMigration` — потерянная
строка здесь это потерянная история, которую Health Connect может уже не отдать
(он гарантирует только 30 дней, а провайдеры чистят данные независимо).

## Модель данных

### `DailySummary` — один календарный день
Первичный ключ — сам `dateEpochDay`, а не автоинкремент. У дня, в отличие от
привычки, **есть естественный уникальный ключ**, поэтому запись сразу
идемпотентна, а Firestore получает стабильный id документа бесплатно —
отдельный `syncId`-UUID (как в habits) здесь не нужен.

Все числовые поля используют **0 как «нет данных»**, не null. Health Connect
законно ничего не знает про большинство метрик в день, когда часы лежали на
зарядке, а 0-vs-null протащил бы nullability через каждый форматтер и график.
Правило применяется последовательно: 0 читается как «неизвестно», поэтому
недельные средние **пропускают нулевые дни**, а не занижают среднее.

### `Workout` — одна тренировка
Первичный ключ — `recordId`, то есть UUID записи из самого Health Connect.
Он же id документа в Firestore. `exerciseType` хранится **сырым int**, не
разрешённым названием: новая версия Health Connect, добавившая вид спорта, не
должна требовать миграции БД. Маппинг в русское название и эмодзи — в
`util/ExerciseTypes.kt`, с падением на «Тренировка» для незнакомых типов
(незнакомый тип — обычное событие, а не баг, и терять такую тренировку нельзя).

## Ключевые механики

### Границы дня — локальные, не UTC
День идёт от локальной полуночи до локальной полуночи. Иначе вечерняя пробежка
у пользователя вдали от UTC уезжала бы на соседний день.

### Сон принадлежит утру, в которое он закончился
Сессия 23:40 понедельника → 07:10 вторника — это **сон вторника**, как считает
и сам Garmin. Иначе вопрос «как я спал сегодня ночью» отвечал бы про не ту ночь.
Реализация: читается окно шире суток, затем фильтр по дате **окончания**.

Стадии: `DEEP`/`LIGHT`/`REM` идут в свои корзины, `SLEEPING` («сон, стадия
неизвестна») — только в общий итог, `AWAKE`/`AWAKE_IN_BED` считаются отдельно и
**не входят** в общий сон, `OUT_OF_BED`/`UNKNOWN` не считаются вообще. Сессия
вовсе без стадий засчитывается целиком как сон — лучше, чем показать ноль.

### Недельные средние — по дням с данными, не по семи
`SummaryRepository.computeWeekSummary()`. Суббота с часами на зарядке не должна
тянуть недельный пульс покоя к нулю. Поэтому рядом со средним всегда
показывается, **на скольких днях оно построено** («в среднем за 4 дня с
записью») — «7 ч 10 мин» из трёх ночей и из семи это разные утверждения.

### Пустой день не записывается
`SummaryRepository.upsertDay()` молча выходит, если день пустой. «Health Connect
ничего не отдал» ≠ «ничего не происходило»: часы могли ещё не синхронизироваться,
а данные дня могут лежать на другом телефоне. Запись нулей превратила бы это
молчание в факт и затёрла бы реальный день, приехавший из Firestore.

По той же причине `WorkoutRepository.replaceDay()` (delete + insert, чтобы
удалённая наверху тренировка не жила здесь вечно) **вызывается только для дня,
который реально прочитался** — иначе сбой разрешений стирал бы историю.

### Синхронизация — перечитывание окна, а не «только новое»
У Health Connect нет фида изменений, подписаться не на что: единственный
триггер — открытие приложения. Окно намеренно шире одного дня (14 дней при
запуске, 90 по кнопке «Загрузить историю»), потому что **Garmin задним числом
дописывает и правит прошлые дни**, когда часы синхронизируются с опозданием.
Читать только новые дни означало бы навсегда оставить эти правки несинхронными.

### Firestore — last-write-wins по `updatedAtMillis`
Обе стороны выводятся из одного и того же Health Connect, сливать по полям
нечего — свежее чтение просто лучше. Без этой проверки старый документ с
другого устройства затирал бы только что перечитанный день.

## Диагностика — `debug/AppLog.kt`

Появился после того, как выяснилось: приложение в нескольких местах
**намеренно** глотает исключения (это правильно с точки зрения UX — одно
отозванное разрешение не должно ронять весь день), но раньше это означало, что
реальная причина «данные Garmin не приходят» не оставляла вообще никакого
следа. `AppLog` не меняет, что глотается — он делает так, чтобы каждый
проглоченный случай записывался.

Два хранилища: кольцевой буфер в памяти (для мгновенного показа во вкладке
Я → Логи) и файл в `filesDir/logs/app.log` с обрезкой по размеру (файл нужен,
потому что синк на старте приложения запускается ДО того, как пользователь
откроет вкладку Я — без файла эти логи терялись бы).

**Что логируется** (сознательно только метаданные, никогда сами значения —
шаги/пульс/минуты сна в лог не попадают, только факт «есть/нет»):
- `HealthConnectReader.runCatchingRead()` — какая секция (шаги, пульс, сон,
  тренировки) не прочиталась и почему. Раньше `catch (e: Exception) { null }`
  без единой записи — это была ровно та дыра, из-за которой «многое не
  подавалось» никак нельзя было продиагностировать
- `HealthSyncManager.syncRange()` — какие разрешения Health Connect НЕ выданы
  (частичный грант — самый вероятный кандидат на «часть данных не приходит»),
  сколько дней записано/пусто за синк
- `FirestoreSyncManager` — раньше `.set()` вызывался вообще без
  `addOnFailureListener`, а у `addSnapshotListener` параметр ошибки просто
  игнорировался (`{ snapshot, _ -> }`). Оба случая означали, что отказ
  `firestore.rules` или обрыв слушателя были неотличимы от «просто нечего
  синхронизировать». Теперь оба логируются

**UI**: вкладка Я → «Логи» — последние 20 записей с подсветкой по уровню,
кнопки «Обновить»/«Поделиться логами» (шлёт файл целиком через тот же
FileProvider-паттерн, что и `export/DataExporter`)/«Очистить». Когда что-то
не работает — первый шаг: попросить пользователя нажать «Поделиться логами»
и прислать файл, а не гадать по скриншотам экрана.

## Экраны

Нижнее меню: **День** / **Неделя** / **Тренировки** / **Я**.

- **День** — стрелками по датам (вперёд упирается в сегодня: завтрашней
  активности не бывает, и листание в пустоту читается как поломка). Плитки
  метрик, сон со стадиями, пульс, список тренировок дня
- **Неделя** — итоги, сравнение с прошлой неделей чипами, график шагов по дням,
  сон (среднее + график), пульс, тренировки недели
- **Тренировки** — весь архив, сгруппированный по датам, плюс итоги за всё время
- **Я** — Health Connect (статус/разрешения), синхронизация, логи (см.
  «Диагностика» выше), аккаунт, экспорт JSON, обновления приложения

## Графики — принятые правила

Проверялись валидатором палитры, а не на глаз, и это дало два реальных
исправления:

- **У тёмной темы свои цвета, а не осветлённые на лету.** Индиго глубокого сна
  из светлой темы даёт контраст 1.75:1 на тёмном фоне — сегмент практически
  невидим. Поэтому `MetricPalette` существует в двух полных наборах
  (`ui/theme/Color.kt`), оба проверены на порог 3:1 к своей поверхности
- **Стадии сна — строки с подписями, а не один stacked-бар.** Односоставный
  индиго-ramp физически не может одновременно держать контраст к тёмному фону,
  минимальную цветность и различимость соседних шагов: самый светлый шаг
  «сереет». Строка со своим названием и длительностью делает цвет лишь
  подкреплением, а не носителем смысла — это и доступнее, и читаемее на телефоне
- Один цвет = одна метрика **везде** (тот же янтарный — шаги и на плитке, и на
  графике, и в строке тренировки)
- Числа и подписи носят текстовые токены, **не цвет серии**
- На недельном графике подписано значение **только у максимального столбца** —
  число над каждым столбцом превращает график обратно в таблицу
- Никаких двух осей Y. Нигде

## Грабли — на чём реально спотыкались

- **`androidx.health.connect:connect-client:1.1.0` требует `compileSdk = 36`.**
  Сборка падает на `checkDebugAarMetadata` с внятным текстом. `targetSdk`
  при этом намеренно оставлен 35 — это поддерживаемая комбинация
- **Kotlin 2.3.20 убрал `kotlinOptions { jvmTarget = "17" }`** — теперь только
  `kotlin { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }` вне блока
  `android {}` (ровно как в atomic-habits-tracker)
- **Плагин Google Services валит сборку без `google-services.json`.** Поэтому в
  репозитории лежит структурно валидная заглушка, а `sync/FirebaseSetup.kt`
  узнаёт её по `project_id` и честно пишет во вкладке «Я», что облако не
  настроено — вместо кнопки входа, которая гарантированно не сработает
- **Health Connect не использует обычный runtime-permission flow.**
  `ActivityResultContracts.RequestMultiplePermissions` здесь молча ничего не
  делает; единственный рабочий путь — `PermissionController.createRequestPermissionResultContract()`
- **Разрешение, запрошенное в коде, но не объявленное в манифесте, просто
  никогда не выдаётся** — без ошибки. Список в `HealthConnectManager.permissions`
  и `android.permission.health.*` в манифесте обязаны совпадать
- **Без `READ_HEALTH_DATA_HISTORY` отдаются только последние 30 дней**,
  независимо от запрошенного диапазона — история тихо обрезается
- **Каждая секция чтения обёрнута отдельно** (`runCatchingRead`). Health Connect
  бросает исключения на совершенно рядовых ситуациях — отозванное разрешение,
  тип записи, который провайдер никогда не писал, обновление провайдера — и ни
  одна из них не должна ронять чтение остальных секций дня
- **Debug-keystore коммитить, фиксированный** — иначе каждая пересборка CI
  получает новый случайный ключ и Google Sign-In (привязанный к SHA-1) ломается
- **`rememberCoroutineScope()` отменяется при уходе с экрана.** Для синхронизации
  — `FitnessSummaryApp.launchPersistent`, иначе диапазон дат оборвётся на середине
- **Route с query-параметром ломает подсветку таба нижнего меню.** Все четыре
  маршрута здесь — голые строки без аргументов; данные между экранами передавать
  через `savedStateHandle`, не через URL
- **Тег релиза `build-<N>` парсит `UpdateChecker`** — менять формат в workflow
  без правки парсера нельзя
- **Логи сборки GitHub Actions недоступны агенту напрямую** (Azure blob storage
  не в списке разрешённых доменов). Обходной путь, который сработал в этом
  проекте: поставить Android SDK прямо в сессии (`sdkmanager` + platform 36) и
  собирать локально — тогда ошибки компиляции видны сразу, без раунд-трипа

## Бэклог — обсуждали, но НЕ реализовали

- **Виджет на главный экран** со сводкой за сегодня
- **Уведомление с утренней сводкой** (сон + готовность) — инфраструктуры
  уведомлений в проекте пока нет вообще
- **Цели** (шаги в день, тренировки в неделю) и прогресс к ним
- **Месячный экран** и тренды длиннее недели
- **Зоны пульса** по тренировке — Health Connect отдаёт серию `HeartRateRecord`,
  сейчас берутся только avg/max
- **Сегменты и круги тренировки** (`ExerciseSessionRecord.segments`/`laps`) —
  читаются, но не сохраняются
- **CSV/PDF-экспорт** — сейчас только JSON
- **Связка с `atomic-habits-tracker`**: тренировка из Garmin автоматически
  закрывает привычку «спорт». Два отдельных приложения, общего хранилища нет —
  потребует либо ContentProvider, либо общего Firestore-проекта
- **Вариант A (self-serve API + Cloud Function)** — если Garmin однажды одобрит
  доступ, добавить второй источник за общим интерфейсом, не переписывая UI:
  Body Battery/Stress/Training Load приходят только этим путём
