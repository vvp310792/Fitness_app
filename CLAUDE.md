# Фитнес-сводка — контекст проекта

Этот файл — сжатая память всего, что было решено и построено в проекте.
Он написан для того, чтобы новая сессия (в том числе в Claude Code) не начинала
с нуля и не переоткрывала уже принятые решения заново.

Приложение делает одно: берёт данные тренировок и восстановления, которые
**Garmin Connect пишет в Health Connect**, и складывает их в честную сводку за
день и за неделю. Оно ничего не измеряет само и ничего не пишет обратно.

Проект — младший брат `atomic-habits-tracker`: те же стек, архитектура,
принципы обновления и стиль. Осознанное повторение, а не совпадение.

## Почему Health Connect, а не Garmin Connect API

Это главное архитектурное решение, и его **не нужно пересматривать без новых
фактов** — оно было принято после проверки, а не по умолчанию.

Официальный Garmin Connect API (и Health, и Activity) — **push-only**. Прямых
REST-эндпоинтов «отдай активности за период» нет, они прямо запрещены условиями
API. Garmin шлёт PING/PUSH на **публичный HTTPS-webhook**, и только после этого
можно забрать данные по callback-URL.

Из этого следует то, что и определило архитектуру:

- **Android-приложение не может быть webhook-приёмником.** Вариант «APK + Garmin
  API» без серверного куска не собирается физически.
- Self-serve режим существует, но даёт доступ только к собственным данным, а
  регистрация периодически закрыта; заявки от физлиц отклоняют — нужно юрлицо.

Рассматривались три пути:

| | Как | Сервер | Что даёт |
|---|---|---|---|
| A | Self-serve API + Cloud Function-вебхук | нужен | всё, что отдаёт API |
| B | **Health Connect** ← выбран | не нужен | шаги, калории, дистанция, пульс, сон, тренировки |
| C | Неофициальная авторизация (garth-подобная) | не нужен | всё, включая Body Battery |

Выбран **B**: бесплатно, без регистрации, без сервера, без серых зон ToS,
работает офлайн.

**Цена решения, которую надо помнить:** Body Battery, Stress, Intensity Minutes,
Training Load, Training Status, VO2max, HRV Status в Health Connect отсутствуют
как типы данных — не потому что не реализовано, а потому что Garmin их туда не
передаёт. Health Connect остаётся основным источником для всего остального
(шаги/дистанция/калории/пульс/сон/тренировки) и работает без единого доп.
шага от пользователя. Для Stress и Body Battery — см. следующий раздел: это
уже реализовано вариантом C, поверх Health Connect, а не вместо него.

Цепочка данных целиком:

```
Часы Garmin ──BLE──> Garmin Connect ──> Health Connect ──> Room ──> UI
                                                            └──> Firestore (между устройствами)
```

Требует Android 14+: именно с него Garmin Connect умеет писать в Health Connect.
На 26..33 приложение ставится и запускается, но честно сообщает, что Health
Connect недоступен.

## Прямой доступ к Garmin (неофициально) — `garmin/`

Реализован вариант **C** из таблицы выше: неофициальная авторизация логином/
паролем, тем же приватным протоколом, что использует официальное мобильное
приложение Garmin Connect. Добавлен **поверх** Health Connect, не вместо —
у большинства установок эта авторизация никогда не пройдена, и всё остальное
приложение работает как прежде. Этот путь даёт **все собственные оценки
Garmin**, которых в Health Connect нет и не будет в принципе: Sleep Score и
Sleep Need, HRV Status, Training Readiness, Training Status/нагрузка/ACWR,
VO2max, Endurance/Hill Score, Body Battery, стресс по зонам, интенсивные
минуты, SpO2/дыхание, вес и состав тела, Training Effect по каждой
тренировке. Плюс сон и пульс покоя — которые Garmin *мог бы* писать в Health
Connect, но на реальном устройстве пользователя не писал (14 дней подряд
`сон=false пульс_покоя=false` в логах при полностью выданных разрешениях).

**Почему именно C, не A.** Официальный self-serve API (вариант A) push-only и
требует сервер-вебхук — уже отклонён по причинам в разделе выше. Вариант C не
требует сервера вообще: это обычные HTTPS-запросы прямо с телефона.

**Протокол выверен по исходникам `garth`** (https://github.com/matin/garth,
референсная Python-реализация того же приватного API), не восстановлен по
памяти — это прямо оговорённый риск (см. «Грабли» ниже), поэтому каждый
эндпоинт и поле сверялись с реальным кодом перед реализацией:

0. `GET sso.garmin.com/mobile/sso/en/sign-in?clientId=...` **до** логина, и
   `GET sso.garmin.com/portal/sso/embed` **после** SSO-успеха, но до обмена
   тикета — оба не несут полезной нагрузки сами по себе, только сессионные
   cookie, которые следующий шаг молча требует. Пропуск любого из двух —
   реальный баг, который был: SSO логинился успешно (тикет приходил), но
   обмен тикета падал с HTTP 400 без них
1. `POST sso.garmin.com/mobile/api/login` — JSON {username, password}. При
   `responseStatus.type == "MFA_REQUIRED"` — второй запрос
   `POST .../mobile/api/mfa/verifyCode` с кодом (метод MFA из
   `customerMfaInfo.mfaLastMethodUsed`, дефолт "email"). SSO-сессия живёт в
   cookie — все запросы этого раздела обязаны идти через один `OkHttpClient`
   с общим `CookieJar` (`InMemoryCookieJar` в `GarminAuthClient.kt`), а сам
   jar обязан сопоставлять cookie по `Cookie.matches()`, не по точному хосту
   ответа — Garmin ставит cookie на весь `.garmin.com`, и они нужны и на
   `connectapi.garmin.com` тоже, не только на `sso.garmin.com`
2. Успех даёт `serviceTicketId` → обмен на **OAuth1**-токен:
   `GET connectapi.garmin.com/oauth-service/oauth/preauthorized?ticket=...`.
   **Этот запрос тоже подписан OAuth1** — двухногим (только consumer
   key/secret, без пользовательского токена, которого на этом шаге ещё нет:
   именно этот запрос его и выдаёт). `GarminOAuth1Signer` в этом режиме не
   добавляет `oauth_token` в параметры вовсе (не пустой строкой — отсутствует),
   а в подписываемую строку параметров обязан попасть весь query этого
   запроса (`ticket`/`login-url`/`accepts-mfa-tokens`), не только `oauth_*` —
   раньше подписи для этого вызова не было вообще, тоже давало HTTP 400
3. OAuth1 → **OAuth2** Bearer:
   `POST .../oauth-service/oauth/exchange/user/2.0`, подписан HMAC-SHA1
   (`GarminOAuth1Signer.kt` — минимальный самописный подписчик, в проекте
   нет OAuth1-библиотеки и заводить её ради одного эндпоинта не стоило).
   Consumer key/secret для подписи — **не в коде**, тянутся во время
   выполнения с `thegarth.s3.amazonaws.com/oauth_consumer.json`
   (community-поддерживаемый файл — если Garmin их сменит, обновится в одном
   месте для всех, кто использует `garth`-совместимый клиент, без пересборки
   приложения)
4. Дальше — просто `Authorization: Bearer <token>` на все data-запросы.
   **OAuth1-токен живёт ~год** — пароль после первого входа больше не нужен,
   новый OAuth2 Bearer перевыпускается тем же одним подписанным запросом (п.3)

**Данные — какой эндпоинт что отдаёт** (все из `garth`, `src/garth/data` и
`src/garth/stats`; JSON-ключи восстановлены из snake_case-полей `garth` его же
регуляркой `((?<=[a-z0-9])[A-Z]|(?!^)[A-Z](?=[a-z])|(?<=[a-zA-Z])[0-9])` → `_`,
поэтому `vo_2_max` ← `vo2Max`, `last_night_5_min_high` ← `lastNight5MinHigh`):

| Таблица Room | Эндпоинт `connectapi.garmin.com/...` | garth-класс |
|---|---|---|
| `garmin_daily_extra` | `usersummary-service/usersummary/daily/?calendarDate=` — шаги, калории, дистанция, этажи, пульс (мин/макс/покоя/7-дневный), стресс (средний/макс/`stressQualifier`), Body Battery (пробуждение/макс/мин), интенсивные минуты (умеренные/интенсивные), бюджет времени (активно/сидя/сон, сек), SpO2, дыхание | `DailySummary` |
| → те же строки | `usersummary-service/stats/stress/daily/{start}/{end}` — секунды в 4 зонах стресса (rest/low/medium/high) | `DailyStress` |
| → те же строки | `usersummary-service/stats/im/daily/{start}/{end}` — `weeklyGoal` интенсивных минут | `DailyIntensityMinutes` |
| → те же строки | `usersummary-service/stats/hydration/daily/{start}/{end}` | `DailyHydration` |
| `garmin_sleep` | `sleep-service/sleep/dailySleepData?date=` — стадии, Sleep Score + оценки компонентов (`qualifierKey`), Sleep Need (`baseline`/`actual`), SpO2/дыхание/стресс за ночь, пульс покоя, `bodyBatteryChange`, температура кожи. Выбран вместо `wellness-service/.../dailySleepData/{username}` — не требует username и богаче | `DailySleepData` |
| `garmin_hrv` | `hrv-service/hrv/{date}` → `hrvSummary` (weeklyAvg, lastNightAvg, baseline, status) | `HRVData` |
| `garmin_readiness` | `metrics-service/metrics/trainingreadiness/{date}` — **список** (пересчитывается в течение дня), берётся последний по `timestamp` | `TrainingReadinessData` |
| `garmin_training` | `mobile-gateway/usersummary/trainingstatus/latest/{date}` → `mostRecentTrainingStatus.payload.latestTrainingStatusData.<deviceId>` + вложенный `acuteTrainingLoadDTO`; `metrics-service/metrics/hillscore?calendarDate=` (тут же `vo2Max`); `metrics-service/metrics/endurancescore?calendarDate=` | `DailyTrainingStatus`, `GarminScoresData` |
| `garmin_body_composition` | `weight-service/weight/range/{start}/{end}?includeAll=true` → `dailyWeightSummaries[].allWeightMetrics[]` | `WeightData` |
| `garmin_activities` | `activitylist-service/activities/search/activities?limit=&start=` (страницами, пока не старше окна) + `activity-service/activity/{id}` → `summaryDTO` (Training Effect, нагрузка, мощность, каденс, Body Battery за сессию) | `Activity`, `Summary` |

Стресс-зоны, цель интенсивных минут и гидратация — range-эндпоинты (один
вызов на окно, страницы по 28 дней), их результат вливается в строку
`garmin_daily_extra` того же дня. Полный таймлайн Body Battery
(`wellness-service/wellness/bodyBattery/events/{date}`) по-прежнему не читается
— дневной сводки достаточно для уровня детализации экрана «День».

Один синк 14 дней ≈ 14×6 + 5 + (число тренировок) запросов; история на 90
дней — несколько сотен, поэтому это отдельная кнопка, не автозапуск.

**Хранение.** Одна таблица на эндпоинт (`data/GarminEntities.kt`), все
ключом по `dateEpochDay`, а не одна широкая строка и не колонки в
`DailySummary`: каждый раздел падает независимо (часы без HRV-сенсора дают
204 на `hrv-service`, у пользователя без весов нет строк веса), и per-table
upsert означает, что одна недоступная фича никогда не блокирует и не
затирает остальные — тот же принцип, что `runCatchingRead` в
`HealthConnectReader`. Установка, где Garmin-логин никогда не настраивался,
видит семь всегда пустых таблиц, а не `DailySummary`, чей смысл тихо зависит
от фичи, которой там нет. **Ничего из этого не уходит в Firestore**: в
отличие от Health Connect (чей источник может быть читаем только на ОДНОМ
телефоне), всё это можно перечитать из Garmin на любом устройстве с логином.

Пароль нигде не персистится — только держится в памяти на время одного
запроса входа. Персистится исключительно OAuth1-пара, через
`EncryptedSharedPreferences` (`GarminTokenStore.kt`, AES-256, ключ в Android
Keystore) — не обычные `SharedPreferences`, это фактически бессрочный пароль-
эквивалент к аккаунту Garmin.

**Сопоставление тренировок.** Health Connect и Garmin описывают одну и ту же
запись с одних часов, поэтому `garmin_activities` матчится к `workouts` по
времени старта (±3 мин, `ui/components/WorkoutRow.kt: matchGarminActivity`) на
этапе отображения, не хранится связь. Совпавшая пара — одна карточка со
строкой Training Effect; несовпавшая Garmin-активность (ручная запись в
Garmin Connect, или до подключения Health Connect) — своя карточка с пометкой
«Garmin».

**Аналитика — `analytics/LifestyleAnalytics.kt`.** Правила поверх метрик
Garmin, без модели: каждый вывод — явный порог и число дней, на которых он
построен, названное прямо в тексте вывода. Пороги — из собственных
рекомендаций Garmin, где они есть (зоны стресса 25/50/75, полосы Body Battery,
окно ACWR 0,8–1,3, цель 150 интенсивных минут = ВОЗ), иначе консервативные
клинические эмпирики (пульс покоя +4 к 3-недельному среднему, SpO2 < 94,
> 10 ч сидя). Sleep debt считается против Garmin Sleep Need (`needActual`),
а не против фиксированных 8 часов — 8 ч только как fallback, когда Garmin
Sleep Need не посчитал. Время отбоя для «стабильности режима» считается в
минутах от 18:00, чтобы 23:30 и 00:30 были в часе друг от друга, а не в 23.

**Честно и прямо пользователю** (UI-текст в `SettingsScreen.kt`, секция
«Garmin напрямую»): это не поддерживается Garmin и может сломаться без
предупреждения при изменениях на их стороне — не «баг», а свойство
неофициального пути.

## Стек и структура

Kotlin + Jetpack Compose (Material3), Room (единственный источник правды для
UI, offline-first), Firebase Firestore (синхронизация поверх Room, не вместо
неё), Firebase Auth (Google Sign-In). Без ViewModel — Compose-локальное
состояние (`collectAsState`/`remember`/`LaunchedEffect`) напрямую поверх Flow
из репозиториев. Осознанное упрощение под масштаб одного разработчика.

```
data/          Entity + Dao + Repository + агрегация недели
health/        HealthConnectManager (доступ/разрешения), Reader (чтение), SyncManager (в Room)
sync/          FirestoreSyncManager, AuthManager, FirebaseSetup
debug/         AppLog — внутриприложенный лог, см. «Диагностика» ниже
garmin/        Неофициальный клиент Garmin Connect (Auth, Api, Sync) — см. выше
analytics/     LifestyleAnalytics — правила-инсайты и тренд-серии поверх Garmin-таблиц
ui/<screen>/   один пакет на экран (day, week, trends, workouts, settings)
ui/components/ переиспользуемые composable, включая графики (Charts, TrendCharts)
export/        DataExporter — JSON-экспорт для анализа
update/        UpdateChecker + ApkInstaller (обновление по GitHub Releases)
util/          чистые функции без побочных эффектов (+ GarminLabels — русские подписи для enum-строк Garmin)
navigation/    Routes + NavHost + нижнее меню
```

Текущая версия БД — **v3** (v1→v2 добавила `garmin_daily_extra`; v2→v3
расширила её до полной дневной сводки Garmin и добавила `garmin_sleep`,
`garmin_hrv`, `garmin_readiness`, `garmin_training`,
`garmin_body_composition`, `garmin_activities` — см. «Прямой доступ к Garmin»
выше). Каждая будущая миграция аддитивна, ничего не
удаляется деструктивно, никогда `fallbackToDestructiveMigration` — потерянная
строка здесь это потерянная история, которую Health Connect может уже не отдать
(он гарантирует только 30 дней, а провайдеры чистят данные независимо).

## Модель данных

### `DailySummary` — один календарный день
Первичный ключ — сам `dateEpochDay`, а не автоинкремент. У дня, в отличие от
привычки, **есть естественный уникальный ключ**, поэтому запись сразу
идемпотентна, а Firestore получает стабильный id документа бесплатно —
отдельный `syncId`-UUID (как в habits) здесь не нужен.

Все числовые поля используют **0 как «нет данных»**, не null. Health Connect
законно ничего не знает про большинство метрик в день, когда часы лежали на
зарядке, а 0-vs-null протащил бы nullability через каждый форматтер и график.
Правило применяется последовательно: 0 читается как «неизвестно», поэтому
недельные средние **пропускают нулевые дни**, а не занижают среднее.

### `Workout` — одна тренировка
Первичный ключ — `recordId`, то есть UUID записи из самого Health Connect.
Он же id документа в Firestore. `exerciseType` хранится **сырым int**, не
разрешённым названием: новая версия Health Connect, добавившая вид спорта, не
должна требовать миграции БД. Маппинг в русское название и эмодзи — в
`util/ExerciseTypes.kt`, с падением на «Тренировка» для незнакомых типов
(незнакомый тип — обычное событие, а не баг, и терять такую тренировку нельзя).

## Ключевые механики

### Границы дня — локальные, не UTC
День идёт от локальной полуночи до локальной полуночи. Иначе вечерняя пробежка
у пользователя вдали от UTC уезжала бы на соседний день.

### Сон принадлежит утру, в которое он закончился
Сессия 23:40 понедельника → 07:10 вторника — это **сон вторника**, как считает
и сам Garmin. Иначе вопрос «как я спал сегодня ночью» отвечал бы про не ту ночь.
Реализация: читается окно шире суток, затем фильтр по дате **окончания**.

Стадии: `DEEP`/`LIGHT`/`REM` идут в свои корзины, `SLEEPING` («сон, стадия
неизвестна») — только в общий итог, `AWAKE`/`AWAKE_IN_BED` считаются отдельно и
**не входят** в общий сон, `OUT_OF_BED`/`UNKNOWN` не считаются вообще. Сессия
вовсе без стадий засчитывается целиком как сон — лучше, чем показать ноль.

### Недельные средние — по дням с данными, не по семи
`SummaryRepository.computeWeekSummary()`. Суббота с часами на зарядке не должна
тянуть недельный пульс покоя к нулю. Поэтому рядом со средним всегда
показывается, **на скольких днях оно построено** («в среднем за 4 дня с
записью») — «7 ч 10 мин» из трёх ночей и из семи это разные утверждения.

### Пустой день не записывается
`SummaryRepository.upsertDay()` молча выходит, если день пустой. «Health Connect
ничего не отдал» ≠ «ничего не происходило»: часы могли ещё не синхронизироваться,
а данные дня могут лежать на другом телефоне. Запись нулей превратила бы это
молчание в факт и затёрла бы реальный день, приехавший из Firestore.

По той же причине `WorkoutRepository.replaceDay()` (delete + insert, чтобы
удалённая наверху тренировка не жила здесь вечно) **вызывается только для дня,
который реально прочитался** — иначе сбой разрешений стирал бы историю.

### Синхронизация — перечитывание окна, а не «только новое»
У Health Connect нет фида изменений, подписаться не на что: единственный
триггер — открытие приложения. Окно намеренно шире одного дня (14 дней при
запуске, 90 по кнопке «Загрузить историю»), потому что **Garmin задним числом
дописывает и правит прошлые дни**, когда часы синхронизируются с опозданием.
Читать только новые дни означало бы навсегда оставить эти правки несинхронными.

### Firestore — last-write-wins по `updatedAtMillis`
Обе стороны выводятся из одного и того же Health Connect, сливать по полям
нечего — свежее чтение просто лучше. Без этой проверки старый документ с
другого устройства затирал бы только что перечитанный день.

## Диагностика — `debug/AppLog.kt`

Появился после того, как выяснилось: приложение в нескольких местах
**намеренно** глотает исключения (это правильно с точки зрения UX — одно
отозванное разрешение не должно ронять весь день), но раньше это означало, что
реальная причина «данные Garmin не приходят» не оставляла вообще никакого
следа. `AppLog` не меняет, что глотается — он делает так, чтобы каждый
проглоченный случай записывался.

Два хранилища: кольцевой буфер в памяти (для мгновенного показа во вкладке
Я → Логи) и файл в `filesDir/logs/app.log` с обрезкой по размеру (файл нужен,
потому что синк на старте приложения запускается ДО того, как пользователь
откроет вкладку Я — без файла эти логи терялись бы).

**Что логируется** (сознательно только метаданные, никогда сами значения —
шаги/пульс/минуты сна в лог не попадают, только факт «есть/нет»):
- `HealthConnectReader.runCatchingRead()` — какая секция (шаги, пульс, сон,
  тренировки) не прочиталась и почему. Раньше `catch (e: Exception) { null }`
  без единой записи — это была ровно та дыра, из-за которой «многое не
  подавалось» никак нельзя было продиагностировать
- `HealthSyncManager.syncRange()` — какие разрешения Health Connect НЕ выданы
  (частичный грант — самый вероятный кандидат на «часть данных не приходит»),
  сколько дней записано/пусто за синк
- `FirestoreSyncManager` — раньше `.set()` вызывался вообще без
  `addOnFailureListener`, а у `addSnapshotListener` параметр ошибки просто
  игнорировался (`{ snapshot, _ -> }`). Оба случая означали, что отказ
  `firestore.rules` или обрыв слушателя были неотличимы от «просто нечего
  синхронизировать». Теперь оба логируются

**UI**: вкладка Я → «Логи» — последние 20 записей с подсветкой по уровню,
кнопки «Обновить»/«Поделиться логами» (шлёт файл целиком через тот же
FileProvider-паттерн, что и `export/DataExporter`)/«Очистить». Когда что-то
не работает — первый шаг: попросить пользователя нажать «Поделиться логами»
и прислать файл, а не гадать по скриншотам экрана.

## Экраны

Нижнее меню: **День** / **Неделя** / **Тренды** / **Тренировки** / **Я**.

- **День** — стрелками по датам (вперёд упирается в сегодня: завтрашней
  активности не бывает, и листание в пустоту читается как поломка). Сверху
  «утренний отчёт» Garmin (готовность / Sleep Score / Body Battery утром /
  ВСР) — если есть Garmin-логин; плитки метрик (Health Connect, с падением
  на Garmin-сводку, когда HC за день пуст); сон (Garmin-ночь с оценками и
  Sleep Need, иначе HC-сессия); Body Battery и стресс по зонам; ВСР;
  готовность с 6 факторами; статус тренировок/VO2max/нагрузка; пульс;
  активность (интенсивные минуты, этажи, бюджет времени, SpO2, вода); вес;
  тренировки дня со строкой Training Effect. Каждая Garmin-карточка
  показывается только при наличии строки — установка без логина видит
  ровно прежний экран
- **Неделя** — итоги, сравнение с прошлой неделей чипами; Garmin-секция:
  интенсивные минуты против недельной цели (прогресс + столбики по дням),
  средние Sleep Score/готовность/стресс/Body Battery, Sleep Score по дням,
  восстановление и нагрузка; график шагов, сон, пульс, тренировки недели
- **Тренды** — 4/8/12 недель; сначала инсайты (`analytics/`), потом графики-
  доказательства в том же порядке: готовность, Sleep Score, длительность сна,
  ВСР с полосой базовой линии, пульс покоя, стресс, Body Battery утром, шаги,
  интенсивные минуты, VO2max, острая нагрузка (пунктир — хроническая), вес.
  Полностью Garmin-зависимый экран: без логина — подсказка идти во вкладку «Я»
- **Тренировки** — весь архив, сгруппированный по датам, плюс итоги за всё время
- **Я** — Health Connect (статус/разрешения), синхронизация, Garmin напрямую
  (вход/MFA, «Синхронизировать» = 14 дней, «История» = 90 дней), логи (см.
  «Диагностика» выше), аккаунт, экспорт JSON (включая все Garmin-таблицы),
  обновления приложения

## Графики — принятые правила

Проверялись валидатором палитры, а не на глаз, и это дало два реальных
исправления:

- **У тёмной темы свои цвета, а не осветлённые на лету.** Индиго глубокого сна
  из светлой темы даёт контраст 1.75:1 на тёмном фоне — сегмент практически
  невидим. Поэтому `MetricPalette` существует в двух полных наборах
  (`ui/theme/Color.kt`), оба проверены на порог 3:1 к своей поверхности
- **Стадии сна — строки с подписями, а не один stacked-бар.** Односоставный
  индиго-ramp физически не может одновременно держать контраст к тёмному фону,
  минимальную цветность и различимость соседних шагов: самый светлый шаг
  «сереет». Строка со своим названием и длительностью делает цвет лишь
  подкреплением, а не носителем смысла — это и доступнее, и читаемее на телефоне
- Один цвет = одна метрика **везде** (тот же янтарный — шаги и на плитке, и на
  графике, и в строке тренировки)
- Числа и подписи носят текстовые токены, **не цвет серии**
- На недельном графике подписано значение **только у максимального столбца** —
  число над каждым столбцом превращает график обратно в таблицу
- На тренд-линии (`TrendChart`) — те же правила: одна серия, точка на день с
  данными, пропуск дня — разрыв, а не ноль; числа (мин/макс/сейчас) текстом
  под графиком, не на точках. Референс — только как полупрозрачная полоса
  (базовая линия ВСР) или пунктир (цель/хроническая нагрузка)
- Никаких двух осей Y. Нигде. Острая и хроническая нагрузка — одна линия и
  пунктир в тех же единицах, не две оси
- Инсайты на «Трендах» помечены тоном (внимание/хорошо/нейтрально) только
  тонкой полоской слева — вердикт несут слова, цвет лишь подсказывает

## Грабли — на чём реально спотыкались

- **`androidx.health.connect:connect-client:1.1.0` требует `compileSdk = 36`.**
  Сборка падает на `checkDebugAarMetadata` с внятным текстом. `targetSdk`
  при этом намеренно оставлен 35 — это поддерживаемая комбинация
- **Kotlin 2.3.20 убрал `kotlinOptions { jvmTarget = "17" }`** — теперь только
  `kotlin { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }` вне блока
  `android {}` (ровно как в atomic-habits-tracker)
- **Плагин Google Services валит сборку без `google-services.json`.** Поэтому в
  репозитории лежит структурно валидная заглушка, а `sync/FirebaseSetup.kt`
  узнаёт её по `project_id` и честно пишет во вкладке «Я», что облако не
  настроено — вместо кнопки входа, которая гарантированно не сработает
- **Health Connect не использует обычный runtime-permission flow.**
  `ActivityResultContracts.RequestMultiplePermissions` здесь молча ничего не
  делает; единственный рабочий путь — `PermissionController.createRequestPermissionResultContract()`
- **Разрешение, запрошенное в коде, но не объявленное в манифесте, просто
  никогда не выдаётся** — без ошибки. Список в `HealthConnectManager.permissions`
  и `android.permission.health.*` в манифесте обязаны совпадать
- **Без `READ_HEALTH_DATA_HISTORY` отдаются только последние 30 дней**,
  независимо от запрошенного диапазона — история тихо обрезается
- **Каждая секция чтения обёрнута отдельно** (`runCatchingRead`). Health Connect
  бросает исключения на совершенно рядовых ситуациях — отозванное разрешение,
  тип записи, который провайдер никогда не писал, обновление провайдера — и ни
  одна из них не должна ронять чтение остальных секций дня
- **`suspend fun`, вызывающая блокирующий `OkHttpClient.execute()` (не async
  callback), сама по себе НЕ переносит выполнение с main-потока.** Health
  Connect'овские suspend-вызовы (`client.aggregate()`/`readRecords()`) —
  честные, неблокирующие корутины из их SDK, отдельная обёртка не нужна.
  Но весь `garmin/` пакет — обычный синхронный OkHttp, и `login()`/
  `dailyExtra()` и т.п. были обнаружены упавшими бы с
  `NetworkOnMainThreadException` при первом же вызове из
  `rememberCoroutineScope()` (по умолчанию Main), пока не завёрнуты в явный
  `withContext(Dispatchers.IO) { ... }`. При этом внутри такого `withContext`
  голый `return`/`return null` для раннего выхода не компилируется — нужен
  `return@withContext`, `withContext` не inline-функция
- **Протокол неофициального Garmin-клиента сверять с реальным исходником
  `garth`, не восстанавливать по памяти.** Этот приватный API уже менялся
  под всеми, кто на него полагается; см. подробный список сверенных
  эндпоинтов/полей в «Прямой доступ к Garmin» выше — каждый URL, заголовок и
  имя JSON-поля там взяты прямо из `github.com/matin/garth`, не угаданы.
  Реальный кейс: первая реализация сверила эндпоинты и JSON-поля, но
  пропустила то, что `garth` делает *между* ними — два «пустых» GET на
  cookie-only страницы (см. п.0 выше) и OAuth1-подпись на обмене тикета —
  и SSO логинился успешно, а обмен тикета стабильно падал HTTP 400. Сверять
  нужно не только эндпоинты/поля, но и каждый вызов в цепочке, включая те,
  чей ответ в коде не используется
- **`GarminOAuth1Signer` подписывает и запросы без пользовательского
  токена** (обмен тикета на OAuth1 — двухногая подпись, только consumer
  key/secret). В таком режиме `oauth_token` должен отсутствовать в
  параметрах вовсе, не быть пустой строкой — `requests_oauthlib` (на чём
  основан `garth`) именно так и делает при `resource_owner_key=None`. Подпись
  также обязана включать query-параметры URL, не только `oauth_*` и тело —
  RFC 5849 §3.4.1.3 требует их в общий набор, но не в саму base string URI
  (та — без query)
- **Kotlin поддерживает вложенные блочные комментарии** — `/*` внутри KDoc
  (например, glob `src/garth/data/*` в тексте) открывает вложенный
  комментарий и даёт «Unclosed comment» в конце файла, а следом — сотню
  «Unresolved reference» во всех файлах, которые на этот класс ссылаются.
  Первая ошибка в списке — единственная настоящая
- **`Cookie.matches()` и JSON-ключи Garmin** — см. «Прямой доступ к Garmin»:
  регулярка `garth` для snake_case не инвертируется однозначно для ключей с
  заглавной аббревиатурой перед цифрой (`averageSpO2Value`), поэтому такие
  поля читаются с несколькими вариантами написания (`JSONObject.float(vararg)`
  в `GarminApiClient`), а не одним угаданным
- **Debug-keystore коммитить, фиксированный** — иначе каждая пересборка CI
  получает новый случайный ключ и Google Sign-In (привязанный к SHA-1) ломается
- **`rememberCoroutineScope()` отменяется при уходе с экрана.** Для синхронизации
  — `FitnessSummaryApp.launchPersistent`, иначе диапазон дат оборвётся на середине
- **Route с query-параметром ломает подсветку таба нижнего меню.** Все четыре
  маршрута здесь — голые строки без аргументов; данные между экранами передавать
  через `savedStateHandle`, не через URL
- **Тег релиза `build-<N>` парсит `UpdateChecker`** — менять формат в workflow
  без правки парсера нельзя
- **Логи сборки GitHub Actions недоступны агенту напрямую** (Azure blob storage
  не в списке разрешённых доменов). Обходной путь, который сработал в этом
  проекте: поставить Android SDK прямо в сессии (`sdkmanager` + platform 36) и
  собирать локально — тогда ошибки компиляции видны сразу, без раунд-трипа
