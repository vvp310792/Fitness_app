# Verified server snapshot contract, v1

Existing PC storage publishes users/{uid}/server_records (immutable JSON or zlib-JSON parts), server_manifest (per-source/per-kind/per-month group manifests), and server_sync/status (updatedAt, records, groups). Status v0 has no commitment to the complete set; unchanged counts and status alone cannot prove a coherent read during an interrupted publication. The app must not replace its verified local data based on v0.

A v1 status adds schemaVersion=1 and manifestSetSha256. The commitment is SHA-256 of UTF-8 lines sorted by group ID, each "groupId<TAB>manifestSha256<TAB>rowCount<LF>". Group SHA is already the SHA-256 of the compact JSON array of ordered immutable part IDs. The server helper tools/server_manifest_contract.py and Kotlin ServerSnapshotContract use the same rule. Each part SHA is the SHA-256 of uncompressed UTF-8 JSON bytes. Verify group identities, counts, hash, contents, and row dates; reject incomplete or conflicting publication, preserve the old active local snapshot. Empty snapshot must be explicitly published (never inferred from a network error).

Integration order: first verify the live source and publication; update the PC publisher using the helper after the complete manifest set and parts have been confirmed (also handle stale groups, without silently deleting raw data); then add a separate transactional Room shadow reader keyed by Firebase user and snapshot generation. Switch active generation only after validating all manifests/parts and unchanged v1 status. No raw data, tokens, or user IDs in logs. Keep existing AppDatabase intact until the normalized shadow dataset is compared with it. The production Firestore rules currently allow owner writes to all nested collections; tighten server-only paths in a separate reviewed deployment, not in this PR. No v1 status is published yet and no production code calls the validator.
